# 施工教训（真实踩过的坑）

本仓库初建时实际发生过的错误。动任何砖之前先读完这一页——它们每一个都浪费过一次完整的调试循环。

## 1. 漏导入：符号用了，import 忘了
`links.js` 用了 `clamp`、`rot` 却不在 import 列表里。`node --check` 只查语法不查引用，
浏览器里表现为"模块被故障隔离悄悄下线"。
**防线**：`node scripts/verify.mjs` 的无头渲染会把每个砖真实渲染 3 帧，ReferenceError 无处遁形。
新砖必须跑体检，别只靠浏览器肉眼看。

## 2. 嵌套数组喂给射线法
点在多边形内判定（PNPOLY 射线法）有两种等价写法：
- 扁平数组版：`ring = Float32Array([lon0, lat0, lon1, lat1, …])`，`ring[i]` 是坐标；
- 嵌套数组版：`ring = [[lon, lat], …]`，`ring[i][0]` 是坐标。
两套索引混用不报错——只是永远返回 false。初建时 `geoPick` 因此全国皆"不命中"，
且因为海洋返回 null 看起来"部分正常"，极具迷惑性。
**防线**：`verify.mjs` 里 `pickAt` 回归测试固定验证成都→China、东京→Japan、大西洋→null。
改动拾取逻辑必须让回归先红后绿。

## 3. 权威对照是最好的裁判
射线法全 miss 时，不要在公式上反复目测——用 `d3.geoContains` 这类权威实现对拍同一份数据，
一步定位"是数据错还是公式错"。当时对拍结果 160:0，立刻锁定是我们传参错误。

## 4. 相机对象 ≠ 相机矩阵
`env.cam` 是 `{ lon0, lat0, zoom, m }`；`rot()` 要的是 `env.cam.m`。
传错对象时坐标算成 NaN，`if (p[2] <= 0.02) continue` 因 NaN 比较为 false 而**不会**跳过，
最终 `ctx.arc(NaN, NaN, …)` 静默画出 0 像素——"没有错误、没有画面"。
**诊断手法**：页内离屏 canvas 单独渲染该砖 + `getImageData` 数像素，立刻见分晓。

## 5. 改 lon0/lat0 必须重算矩阵
直接赋值 `cam.lon0 = 78` 不会更新 `cam.m`，渲染与拾取仍用旧视角。
一律走 `engine.setView(lon, lat, zoom)`。

## 6. 渐变方向
`createLinearGradient(x0, y0, x1, y1)` 的 stop(0) 在 (x0,y0) 端。
昼夜渐变曾把暖光放在背阳侧——物理错了还很难一眼看出。
凡是"方向性"视觉，先在纸上确认端点，再看效果。

## 7. 每段一描边的性能陷阱
120 条航线 × 31 段逐段 `stroke()` ≈ 一帧 4000+ 次绘制调用，帧率从 60 掉到 18。
**手法**：一条航线合成一条路径（背面处断笔），一次 stroke；合批优先于删减数据。

## 8. 环形数据的扫描起点
可见半球裁剪时，从"任意点"开始扫描会导致首尾段缺入边/出边。
先旋转到第一个背面点再扫描，每个可见段才有确定的入点与出点（二分求地平线交点）。

## 9. 数据要先抽样核对再全量转换
接入新 API 先抽 2-3 个已知值（中国人口、美国 CO₂）人工核对，再写全量转换。
World Bank 端点的 `id` 字段在不同端点含义不同（/country 是 ISO3，indicator 行里是 ISO2），
字段名靠猜必翻车，先看真实响应。

## 10. 单砖故障隔离
引擎对每块砖的 render 包 try/catch，坏砖下线并记录到 `engine.errors`，
一块砖的异常不能拖死整个世界的渲染循环。诊断时先看 `window.__world.errors`。

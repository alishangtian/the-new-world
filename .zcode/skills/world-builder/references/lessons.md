# 施工教训（真实踩过的坑）

每一条都在本仓库的施工中真实发生过、浪费过一次完整的调试循环。动代码前先读完。

## 1. 漏导入：符号用了，import 忘了
`node --check` 只查语法不查引用；浏览器里表现为"模块被故障隔离悄悄下线"或整个加载失败。
**防线**：verify/accept 的语法门 + 冒烟测试。新代码必须过门，别只靠肉眼。

## 2. 权威对照是最好的裁判
判定逻辑可疑时，不要反复目测公式——与权威实现对拍同一份数据（如 d3.geoContains），
一步定位"是数据错还是逻辑错"。当年对拍结果 160:0，立刻锁定传参错误。

## 3. 改状态字段 ≠ 状态生效
直接赋值 `cam.lon0 = 78` 不会重算派生量（旋转矩阵），渲染与拾取仍在用旧状态。
**模式**：凡是派生状态，只通过显式方法改（如 `engine.setView`），不裸改字段。

## 4. 对象简写引用不存在的标识符 = 模块加载即崩
`handlers = { world_state, ... }` 里 `world_state` 从未定义 → 整个模块 ReferenceError，
表现为"服务器启动但毫无响应"。错在 stdio 协议上更隐蔽：客户端只看到超时。
**诊断**：手动喂一条消息、带上 stderr 看全量输出。

## 5. 升级要接全链路：数据加了，loader 没加 = 白加
迭代 002 曾把 quakes.json 落了库、写了砖块，但 main.js 的 boot 还只 fetch 三个旧文件——
"有错误、没画面"，且页面缓存让旧 main.js 存活，极具迷惑性。
**模式**：新增资产时，沿着 fetch → 状态 → 消费者 全链路打勾；浏览器验证用带参 URL 绕缓存。

## 6. 缓存是迭代验证的天敌
静态服务器 + 浏览器缓存会让"明明改了却没生效"。
**手法**：验证时用带参 URL（?v=N）强制绕过；CI 里则根本不存在缓存问题。

## 7. 数据要先抽样核对再全量转换
接入新来源先抽 2–3 个已知值人工核对，再写全量转换。
字段名靠猜必翻车——同一 API 的不同端点，`id` 字段含义可以完全不同（ISO2 vs ISO3）。

## 8. 一次调用一个副作用，验收要能分辨"谁没生效"
点击没反应时，先分开验证：拾取函数本身对不对（纯函数可直接调）→ 事件有没有到达目标
（挂一次性监听数次数）。两步定位，比来回猜快得多。

## 9. 单点故障隔离
引擎对每块砖的 render 包 try/catch，坏砖下线并记录，渲染循环永不中断。
诊断先看 `engine.errors`——但记得：隔离不是修复，error 记录清零前别宣布健康。

## 10. 账本一致性的自动化
人读总览（BACKLOG.md）与机器工单（orders/*.json）两处状态必然漂移——
漂移不可怕，没有"漂移即 FAIL"的检查才可怕。verify 负责抓漂移。

## 11. `kubectl apply` 会回退 `kubectl set image`
声明式清单与命令式修改混用：`set image` 改了线上镜像，之后 `apply` 旧清单把镜像 tag 回退——
Pod 看似 Running，跑的却是旧代码（grep 容器内文件 vs 镜像文件才定位到）。
**纪律**：镜像 tag 的唯一真源是清单文件；升级 = 改清单 → apply，不要用 set image 抄近路。
